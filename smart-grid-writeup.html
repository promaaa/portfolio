Smart Grid API — Vert.x + JPA

Java 21 • Vert.x Web • JPA (EclipseLink) • PostgreSQL • Docker Compose

Abstract — A compact backend for a simulated smart grid. It ingests sensor data over HTTP (wind turbines) and UDP (solar panels), persists it with JPA, and exposes a clean REST API for dashboards: persons, grids, sensors, measurements, and simple production/consumption aggregations. Served with OpenAPI docs and a one‑command Docker setup.

1. Motivation & Constraints

The goal is to provide a teaching‑friendly backend that demonstrates sensor ingress, time‑series persistence, and REST design over a realistic smart‑grid domain. The code favors clarity and testability over framework magic.

  • Scope: Producer/consumer sensors, people and grids, measurements, datapoints.
  • Ingress: Wind via HTTP JSON, Solar via UDP text.
  • Persistence: JPA + PostgreSQL, explicit transactions.
  • API: CRUD‑like routes and measurement queries, OpenAPI docs.

2. Domain Model

Core entities are intentionally simple and relatable. A Grid contains Person and Sensor instances. Sensors subclass into Producer and Consumer, then into concrete types (e.g., SolarPanel, WindTurbine, EVCharger). Each sensor offers Measurement definitions, which own time‑series DataPoints.

3. Architecture

The backend is a single Vert.x application that wires a Router with small handler classes. Persistence uses JPA (EclipseLink) with explicit transactions. A tiny service (EnergyService) centralizes “energy accumulation” logic. A UDP server ingests solar panel telemetry.

4. Sensor Ingress (HTTP + UDP)

Two ingress paths mirror realistic devices. Both accumulate energy as Wh with E[n] = E[n-1] + power × (1/60 h) assuming a 60‑second sampling period.

  • Wind (HTTP): POST /ingress/windturbine with JSON payload.
  • Solar (UDP): Datagram payload id:temperature:power:timestamp.
// HTTP JSON: /ingress/windturbine
{
  "windturbine": 2,
  "timestamp": 1741334062,
  "data": { "speed": 123.4, "power": 523.6 }
}

// UDP text: id:temperature:power:timestamp
2:25.4:523.6:1741334062

On success, HTTP returns {"status":"success"}; UDP is fire‑and‑forget. Errors yield structured JSON with error and an appropriate status code.

6. Aggregations

/grid/{id}/production and /grid/{id}/consumption compute a grid‑level scalar by summing each sensor’s latest datapoint on the appropriate measurement (total_energy_produced or total_energy_consumed). The implementation uses concise native SQL to select the most recent datapoint per measurement, then sum.

// Pseudocode
SELECT SUM(latest.value)
FROM datapoint latest
JOIN measurement m ON m.id = latest.measurement
JOIN sensor s ON s.id = m.sensor
WHERE s.grid = :gridId AND m.name = 'total_energy_produced'
AND latest.timestamp = (
  SELECT MAX(d2.timestamp) FROM datapoint d2 WHERE d2.measurement = latest.measurement
);

7. Persistence & Transactions

  • JPA Entities: Joined inheritance for sensors keeps subtype columns in dedicated tables.
  • Transactions: Handlers open small transactions only when mutating; read paths are pure queries.
  • Accumulation: EnergyService queries the previous energy datapoint (if any) before persisting the next one.
  • Config: DB via DB_URL or DB_HOST/DB_PORT/DB_NAME plus DB_USER/DB_PASSWORD.

8. DevEx & Tooling

  • OpenAPI: Spec embedded at src/main/resources/openapi.yaml, served at /openapi.yaml and /docs.
  • Docker Compose: One command boots Postgres, backend, demo frontend, and Adminer.
  • HTTP Collection: docs/api.http for VS Code/IntelliJ makes endpoints quick to try.
  • CI: GitHub Actions build with JaCoCo coverage; publishing via Maven if desired.
  • CORS: Permissive for easy local dashboard integration.

9. Security & Correctness

  • Input validation: Structured errors with { error: string }; 404 for missing resources; 400 for malformed IDs/payloads.
  • UDP trust: UDP ingress is intended for controlled networks or demos; wrap with network ACLs in production.
  • Transactions: Mutations are atomic with rollback on exceptions.
  • Principle: Keep handlers small and side‑effect boundaries explicit.

10. Roadmap

  • Generate typed clients from OpenAPI (TypeScript‑Fetch, Java).
  • Extend Testcontainers tests to cover handler flows.
  • More fine‑grained auth and per‑route CORS in prod settings.
  • Batch ingest endpoints and backpressure for higher throughputs.
  • Retention policies and rollups for long‑term datapoints.

11. Quick Start

# 1) Launch full stack
cd smart-grid-api
docker compose up -d

# 2) Explore
open http://localhost:8080/docs
open http://localhost:8081   # Adminer (db/test/test)
open http://localhost:8082   # Demo frontend

# 3) Try sample routes (or use docs/api.http)
curl http://localhost:8080/persons
curl http://localhost:8080/grid/1/production

# 4) Local dev only
./gradlew run
