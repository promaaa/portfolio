1. Chess Engine Architecture (0x88)

A small, readable engine built on the 0x88 board model: compact indexing, fast bounds checks, simple move generation, and a reversible state with perft validation.

For fast, simple move generation I use the classic 0x88 board representation. The idea: store the board in a 128‑element array (8 ranks × 16 files). Playable squares are indices where (sq & 0x88) == 0. Any step that crosses the board boundary flips bit 0x88, so out‑of‑bounds is a single, branch‑cheap check.

2. Piece Detection & LED Display

A grid of magnetic sensors under the board tracks piece positions, while an LED matrix provides intuitive visual feedback.

Reed Sensor-Based Detection

The system uses 64 reed sensors (Hall effect) placed under each square of the 8x8 grid. A small neodymium magnet is embedded in the base of each chess piece. When a piece is placed on a square, the sensor detects the magnetic field, registering the piece's position. This method provides a reliable, binary state of the entire board at any moment, which is essential for the game logic.

LED Matrix Display

Visual feedback is handled by two HT16K33 LED matrix driver modules. This system can:

  • Indicate possible moves for a selected piece.
  • Highlight the last move made by the opponent or the robot.
  • Display suggestions from the AI.
  • Create visual effects for special events like captures, promotions, or checkmate.

The HT16K33 modules are connected to the main controller via I2C, each controlling multiple LED segments for board illumination.

3. Real-Time Chessboard Detection & Tracking

In this project, I developed a real-time detection and tracking system specifically for video, using a two-step approach that combines the power of Convolutional Neural Networks (CNN) for initial detection with an extremely fast tracking algorithm to maintain localization in successive images. This system complements the reed sensor system, helping to resolve issues with illegal moves or doubts about piece positions by providing visual confirmation.

Here are the exact components of this advanced model I implemented:

1. Detection Phase (Step 1)

This phase is used to find the chessboard in the initial image or if tracking has been lost.

  • Neural Network: The model uses a Convolutional Neural Network (CNN).
  • Architecture: It is a classic classification architecture based on a CNN pyramid plus Max Pool.
  • Performance: This model achieved 96% accuracy. It typically runs in about 30 milliseconds per image.

2. Tracking Phase (Step 2)

Once the chessboard points have been located (by the detection phase), the system switches to the tracking step for subsequent video frames, which generally do not change much.

  • Tracking Algorithm: It uses a classic keypoint tracking algorithm.
  • Specific Implementation: The algorithm I used is the Lucas-Kanade algorithm (LK algorithm).
  • Speed: The LK algorithm is extremely fast, running on the order of milliseconds.
  • Fallback Logic: If the system loses track of the chessboard during tracking, it returns to the first step (CNN detection).

The combination of these two steps allows for a real-time chessboard detector.

Model in Development (YOLO)

At the time of this project, I was also working on a YOLO chessboard detection algorithm. YOLO (You Only Look Once) is a very performant machine learning technique, but the details of its implementation were not yet finalized.

5. Full 8×8 Board Architecture

The production board is orchestrated by a Raspberry Pi 5, which centralizes game logic, AI, and communication with peripherals, including a dedicated microcontroller for robotics.

3D Design & Modeling

Before fabrication, the entire chessboard structure and enclosure were designed in CAD software to ensure precise fit and alignment of all components.

Electronics Architecture

The final architecture is built on the principles validated in the 2x2 PoC, scaled up for the full board.

  • System Brain: A Raspberry Pi 5 running Raspberry Pi OS and the main Python script. It handles the AI, game logic, and communicates with other components.
  • LED Control: Two HT16K33 LED driver modules are connected to the Pi via I2C for board illumination.
  • Piece Detection: The 64 reed sensors are read via MCP23017 I/O expanders, which communicate with the motor controller or the Pi.
  • Motor Control: An ESP32 microcontroller receives motion commands from the Pi via a serial (UART) link. It drives the stepper motors using A4988 or TMC2209 drivers and controls the electromagnet with a MOSFET.

Software

The main game logic runs on the Raspberry Pi using Python. Two versions are available: chess_game_v1.py (basic) and chess_game_v2.py (advanced with opening book support).

6. Mechanical Platform & Manipulator

A two-axis XY gantry system, concealed beneath the playing surface, moves the pieces precisely using an electromagnet.

Architecture & Operation

The robot is a two-axis Cartesian system (X and Y) using MGN12 linear rails and GT2 belts, driven by NEMA17 stepper motors. This design ensures smooth and accurate movement.

  • The X-axis moves a carriage horizontally.
  • The Y-axis moves the longitudinal rail supporting the electromagnet.

To move a piece, the Raspberry Pi sends the start and end coordinates to the microcontroller. The robot positions the electromagnet under the source square, activates it to grip the piece, moves to the target square, and deactivates it to release the piece.

7. Electronics Design & Schematics

Detailed circuit schematics for the sensing matrix, LED drivers, electromagnet control, and stepper motor drivers.

Reed Sensor Matrix (8×8)

The 64 reed switches are arranged in a keyboard-style matrix with anti-ghosting diodes. This reduces the required GPIO pins from 64 to just 16 (8 rows + 8 columns), while preventing false detections when multiple pieces are present.

LED Matrix Driver Architecture

Two HT16K33 LED matrix driver modules are controlled via I2C, each with a unique address. The HT16K33 provides 16×8 LED driving capability with built-in key scanning and PWM dimming, simplifying the board illumination system.

XY Gantry Stepper Drivers

Two A4988 (or DRV8825) stepper drivers independently control the X and Y axis NEMA 17 motors. Configured for 1/16 microstepping, they provide smooth motion with 3200 steps per revolution. The ESP32 generates step pulses and direction signals.

Bill of Materials (BOM)

Key components used in the electronics subsystems:

  • Controllers: Raspberry Pi 5 (4GB), ESP32-DevKit-V1
  • LED Drivers: 2× HT16K33 LED matrix modules
  • Motor Drivers: 2× A4988 or DRV8825 stepper drivers
  • Sensors: 64× KSK-1A85 reed switches, 64× 1N4148 diodes
  • Actuators: 2× NEMA 17 steppers (1.2A/phase), 1× 12V electromagnet (2kg holding force)
  • Power: IRLZ44N MOSFET, 1N4007 flyback diode, 100µF decoupling caps
  • LEDs: 648× 3mm red LEDs (8 matrices × 81 LEDs)

Power Budget

The system requires two voltage rails:

  • 5V Rail: Raspberry Pi 5 (3A), ESP32 (0.5A), LED matrices (1-3A) = ~6.5A max → Buck converter 12V→5V (8A rated)
  • 12V Rail: 2× NEMA 17 steppers (2.4A), electromagnet (0.8A) = ~3.2A → 12V 4A power supply
  • Total power consumption: ~55W typical, ~71W maximum

8. Edge AI Chess Engine

This section presents ZENITH, a chess engine designed for deployment on resource-constrained embedded systems. The engine achieves master-level play (ELO 2100–2400) on a Raspberry Pi 5 through 44 algorithmic optimizations, demonstrating that classical search techniques remain competitive with neural approaches when computational resources are limited.

8.1 Motivation and Design Constraints

Edge AI deployment introduces constraints absent in cloud-based systems: limited memory (4–8 GB), no GPU acceleration, and strict latency requirements for interactive play. Modern neural-network-based engines such as LCZero or AlphaZero achieve superhuman performance but require significant computational resources for inference—typically GPUs or TPUs processing thousands of neural network evaluations per second.

On a Raspberry Pi 5 (ARM Cortex-A76, 2.4 GHz), neural network inference drops to approximately 500–1,000 positions per second, resulting in response times exceeding 10 seconds per move at reasonable search depths. This latency is unacceptable for interactive robotic chess. Our approach instead maximizes algorithmic efficiency: achieving high playing strength through carefully orchestrated classical techniques rather than expensive evaluation functions.

8.3 Search Algorithm

The search subsystem implements a layered approach where each technique builds upon the previous. The base algorithm is NegaMax with Alpha-Beta pruning, which reduces the effective branching factor from approximately 35 to roughly 6 in well-ordered trees.

8.3.1 Iterative Deepening

Rather than searching to a fixed depth, the engine iteratively increases search depth (1, 2, 3, ...) until the time allocation expires. This approach provides "any-time" behavior—a legal move is always available—and enables aspiration windows by using previous iteration results as bounds. The overhead is negligible due to transposition table caching.

8.3.2 Principal Variation Search (PVS)

After searching the first move with a full window [α, β], subsequent moves are searched with a null window [α, α+1]. If a move scores above α, it is re-searched with the full window. This technique reduces node count by approximately 30% when move ordering is effective.

8.3.3 Null Move Pruning

The null move heuristic tests whether the current position is so favorable that even passing (making no move) would result in a beta cutoff. A reduced-depth search (R=2 at depth ≤6, R=3 otherwise) is performed after the null move. This technique is disabled in check and in endgames where zugzwang is common. Expected node reduction: 25–40%.

8.3.4 Quiescence Search

To avoid the "horizon effect," the search extends indefinitely on tactical sequences (captures, promotions). A stand-pat cutoff terminates lines where not capturing is already sufficient. Delta pruning (threshold: 975 centipawns) skips captures that cannot possibly improve alpha even with a queen gain.

8.3.5 Late Move Reductions (LMR)

Moves searched late in the move list are likely inferior and thus searched at reduced depth. The reduction formula is: R=1 for moves 3–5, R=2 for moves 6+. If a reduced-depth search returns a score above alpha, a full-depth re-search is performed. This yields approximately 25% node reduction with minimal accuracy loss.

8.4 Selective Pruning

Beyond the fundamental search enhancements, several pruning techniques eliminate subtrees that are provably or heuristically unlikely to affect the result:

  • Reverse Futility Pruning: At shallow depths (≤4), if the static evaluation minus a depth-dependent margin (120 cp × depth) exceeds beta, the node is immediately pruned.
  • Futility Pruning: Quiet moves are skipped when the static evaluation plus margin (200 cp × depth) falls below alpha, as they cannot improve the position sufficiently.
  • Late Move Pruning: After examining N quiet moves (N = 3 + depth²), remaining quiet moves are pruned entirely at shallow depths.
  • Static Exchange Evaluation (SEE): Captures with negative SEE values (<-100 cp) are pruned in quiescence search, avoiding costly exploration of losing exchanges.

8.5 Move Ordering

Alpha-Beta efficiency is critically dependent on move ordering. An optimally ordered tree achieves a branching factor of √b rather than b. The engine employs a priority scheme with the following order:

  1. Transposition Table Move (priority: 9×10⁸): The best move from a previous search of the same position is tried first, yielding immediate cutoffs in approximately 40% of nodes.
  2. Winning Captures by MVV-LVA (priority: 10⁷): Captures are ordered by (victim value − attacker value), prioritizing PxQ over QxP.
  3. Killer Moves (priority: 10⁶): Four non-capture moves that caused beta cutoffs at the same depth in sibling nodes are maintained per ply.
  4. History Heuristic: A 64×64 table tracks how often each (from, to) move pair causes cutoffs, weighted by depth².
  5. Continuation History: Extended history tracking for move pairs (previous move → current move), capturing tactical patterns with weight ×2.

8.6 Position Evaluation

The evaluation function combines material counting with positional assessment. Rather than training a neural network, we employ PeSTO (Piece-Square Tables Only), a set of 768 hand-tuned values (6 piece types × 64 squares × 2 game phases) that encode positional knowledge.

8.6.1 Tapered Evaluation

The game phase is computed from remaining material. The final score is a linear interpolation between middlegame and endgame evaluations: 

phase = min(24, piece_values_sum) / 24
eval = mg_score × phase + eg_score × (1 - phase)

8.6.2 Supplementary Terms

Beyond piece-square tables, the evaluation incorporates:

  • Mobility: +5 cp per legal move (middlegame), +10 cp (endgame)
  • Pawn Structure: Doubled pawns (−10/−20 cp), isolated (−15/−20 cp), passed (+20/+40 cp)
  • King Safety: Open file penalty (−30 cp), semi-open (−20 cp), pawn shield bonus (+10 cp per pawn)
  • Bishop Pair: +50 cp for possessing both bishops
  • Rook Placement: Open file (+20 cp), connected rooks (+10 cp)

Material values were calibrated using Texel tuning on a dataset of 725,000 positions: P=82, N=337, B=365, R=477, Q=1025.

8.10 Conclusion

This work demonstrates that classical game-tree search, when systematically optimized, remains a viable approach for edge AI chess engines. The combination of 44 well-established techniques achieves a measured improvement of +1,000–1,200 ELO over a baseline Alpha-Beta implementation, reaching master-level play on a Raspberry Pi 5 without GPU acceleration or cloud connectivity.

The key insight is that algorithmic efficiency—through aggressive pruning, effective move ordering, and lightweight evaluation—can compensate for the absence of neural network sophistication in resource-constrained environments. This approach is particularly suitable for embedded robotic systems where latency, offline capability, and energy efficiency are critical constraints.
